# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FirmiCore is a multi-tenant maintenance-management platform (CMMS): machine registry, breakdowns, work orders, PM scheduling, inventory/parts, contractors, shift handovers, training, triage/troubleshooting, OEE, Kaizen, audits, and analytics. Built with React + TypeScript + Vite, backed by Firebase (Auth, Firestore, Storage, Cloud Functions).

**The repo also contains a legacy/unused Vue scaffold** (`src/App.vue`, `src/main.js`, and the generic Vue boilerplate in `README.md`) — this is dead weight, not the active app. The real entry point is `src/main.tsx` → `src/App.tsx` → `src/router/AppRouter.tsx`. Don't edit the Vue files; they aren't wired to anything.

## Git workflow

Do not commit directly to `main`. For every fix or change, create a feature branch (e.g. `fix/<short-description>` or `claude/<short-description>`), commit there, and open a PR into `main` instead of pushing straight to it.

## Working with the owner

- The owner writes requests in English and Sinhala, often as several tasks in one message or added mid-task. Keep a task list of every request (TaskCreate/TaskUpdate) and finish each one, in the order given unless told otherwise.
- When any task or step fails, is skipped, or can't be verified (a check that wouldn't run, a missing credential, a deploy-time step only the owner can do), review it before finishing and report it **in Sinhala**: what failed, why it failed, and what should be done to fix it. Never present such a step as done.
- **Quality bar:** always build code and fulfil every requirement and task 100% correctly, without errors. Run the repo's checks (`npx tsc --noEmit -p .`, `npx vitest run`, `npx eslint` in `functions/`, and `rules-tests` when rules change) before pushing, and re-read the diff for mistakes. Do the tasks one at a time, in order, not in parallel.
- **Final summary (always, in Sinhala):** when everything is done, finish with a Sinhala summary that says (1) what was completed, (2) what the owner still has to do (deploys to check, console steps such as TTL policies or disabling providers, manual tests), (3) any actions to save/keep for later, and (4) anything that failed or couldn't be verified, why, and how to fix it.
- **Before every merge, check CI:** read the PR's check runs (`get_check_runs`). Merge only when all of them have finished and passed; if one is queued/in progress, wait for it, and if one fails, fix it first. Never merge on red or unfinished CI.
- Open a PR for every change (never commit to `main`). Merge only when the owner asks for it; a merge approval for one PR does not carry over to later ones.

## Architecture

### Multi-tenancy and auth
- Firebase Auth + a Firestore `users/{uid}` collection holds the app-level user profile (role, `siteId`, etc.); auth state lives in a Zustand `authStore` (`src/store/authStore.ts`).
- **Every tenant-scoped document carries a `siteId`**, and queries/security rules filter on it. When adding a new collection or query, always scope by the current user's `siteId`.
- **Plant isolation is enforced by `firestore.rules`** (`myPlantId()` / `plantVisible()`): every role but admin is confined to its own plant (users without a plant are company-wide) on `machines` (`plantId`), `workOrders` / `breakdown_tickets` / `pm_history` (`machinePlantId`), `pm_schedules` (`plantId`) and `notifications` (`plantId`, null = every plant) — work assigned to / supervised by the caller, tickets they attend and notifications addressed to them stay visible. Records get their plant from their machine (`functions/src/machines/plantStamps.js` stamps, backfills and moves open work with a machine). **Every list query on those collections must spread `plantConstraints('<collection>')` from `src/lib/plantQuery.ts`** — rules are not filters, so a query without it fails for plant-scoped users; one that also orders / ranges needs a composite index with the plant field. Plan-limit counts go through the `getPlanUsage` callable, since plant users can't count other plants.
- `src/lib/firebase.ts` is the single Firebase init point (app, auth, db, storage, functions) — import from there rather than re-initializing.
- **Deactivated users** (profile `status: 'inactive'`) lose access everywhere: `onCompanyUserWritten` (`functions/src/auth/userAccess.js`, plus the hourly `enforceInactiveUsers`) disables the Firebase Auth login (no sign-in with that email on any device), revokes refresh tokens and mirrors role/plant/department/status onto `users/{uid}`; `getUserData()` in `firestore.rules` resolves an inactive mapping to a placeholder that matches no company/role. Only admin (or HR for other non-admins) changes role/plant/department/status — nobody edits their own. Callables check the caller with `requireMember` / `requireOwnCompany` (`functions/src/lib/access.js`), which also reject anonymous and inactive accounts.

### Role-based access control
- **9 roles**: `admin`, `plant_manager`, `supervisor`, `technician`, `store_keeper`, `hr_officer`, `trainee`, `floor_operator`, `safety_officer` (defined in `src/types/auth.ts`; note `UserRole` is also separately declared in `src/types/breakdown.ts` — a known duplication, so the role string must be added to **both** unions). `safety_officer` is an EHS role that now shares admin/plant_manager's Manager Dashboard (`/app/dashboard/manager`, its default landing page) and Analytics (`/app/analytics`, "Safety" tab) instead of its own dedicated Safety Dashboard/Analytics pages — those legacy pages under `src/modules/safety` (`SafetyDashboard.tsx`, `SafetyAnalyticsPage.tsx`, routes `/app/safety/dashboard` and `/app/safety/analytics`) still exist and are still routable, just no longer linked from safety_officer's nav or used as their landing page (same "orphaned but built" pattern as `tpm`/`fives`). Its Safety nav tab now mirrors admin's: Work Permits (Permit-to-Work with categories + precautions on the `work_permits` collection), Safety Cases, and Safety Trainings (session scheduling, `/app/training/manage/safety-trainings`) — the Safety Cases page itself still gives safety_officer the full case board (triage/close any case) while every other role in that tab sees only cases reported to them, since that's driven by role inside `SafetyCasesPage`, not by which nav entry links there. **Contractor safety training** is the one safety-training flow that is *not* in-app: contractor team members (`contractors/{id}/technicians`, no logins) get a tokenised link to a public form (`/safety-training/:token`, `PublicSafetyTrainingPage`) backed by the `safetyTrainingInvites` collection and three callables in `functions/src/safetyTraining/` (email the link, load the form, submit — scoring, attachments and the 3-attempt/due-time limit are enforced server-side, and only the final submission is stored — `attempts` holds at most that one entry, a resubmit replaces it and deletes its files, `attemptsUsed` is the count; the browser never reads `safetyTrainingInvites` for the visitor). After safety-officer sign-off a Contractor Safety Card (`safetyCertificates`, 3.5 × 2 in two-page PDF with the issuing company's name/logo, verified qualifications, the officer's signature and a QR code — `src/lib/safety/safetyCardPdf.ts` builds it, `safetyCardDownload.ts` gathers logo/photo/live company name) can be issued — only after a digital sign-off (`signOff` on the invite: verified qualifications + drawn signature) with qualifications read from the team member's profile (`contractors/{id}/technicians/{tid}` — `certifications` text + `certificationDocuments` files), never typed on the public form; scanning it (`/safety-card?id=…` or the in-app scanner on Safety Cases) pre-fills a contractor safety case against the holder. Company users keep the old `trainingAssignments` flow (`SafetyTrainingAssignDialog` → `createModuleAssignment`) with no email and no card — don't route them through the invite path. Safety cases (incident/near-miss/hazard/unsafe-act) live in the `safety_cases` collection — any company member can report one; `canManageSafety()` (safety_officer + supervisors + managers) triages/closes them and issues permits. Beyond its trimmed sidebar it still has company-wide read access to the operational modules by route/rules, with no repair/write actions.
- **Platform superadmin (Lumora Ventures staff)** is not a tenant role: it's the Firebase Auth custom claim `superadmin: true`, checked by `isSuperadmin()` in `firestore.rules` and `requireSuperadmin()` in `functions/src/platform/`. The console lives at `/platform` (`src/pages/platform/`, own shell `PlatformLayout`, English-only internal tool) and reads almost everything through the `platform*` callables (companies, Stripe payments, reminders, user login changes, audit log in `platformAuditLog`). Access: only accounts whose verified email is in `PLATFORM_SUPERADMIN_EMAILS` (functions/.env) can activate themselves on `/platform`; there is intentionally no in-app way to grant superadmin to other accounts. Company admins talk to Lumora through `supportRequests` (+ `messages` subcollection) at `/app/support-requests`.
- **Company registration approval**: `registerCompany` creates the company with `approvalStatus: 'pending'` (enforced by the `companies` create rule, along with `status: 'trial'` and `plan: 'starter'`; clients can never change the approval fields). `ProtectedRoute` sends every user of a pending/rejected company to `/app/pending-approval` (`PendingApprovalPage`, live — approval lets them in without a reload). Superadmins approve/reject via `platformUpdateCompany` (`approve` restarts the 7-day trial from the approval date; both email the company admin); the Companies page filters by approval and the nav shows a pending badge from `registration` alerts in `platformNotifications` (written by `onCompanyRegistered`, which also emails Lumora). The free trial is 7 days everywhere (`registerCompany`, `approve`; the `companies` create rule rejects a client-set `trialEndsAt` beyond ~7 days); trials saved before that change are lowered with `node seed/capTrialsTo7Days.mjs [--apply]`. Companies without the field predate approvals and count as approved (`src/lib/companyApproval.ts`). The gate is client-side + rules on the approval fields; Firestore rules don't check approval on every tenant collection.
- **Lumora sales pipeline (platform console, superadmin only)**: leads from outside marketing live in `platformLeads` (status pipeline new → called/not answered/follow-up → demo booked/done → negotiation → closed won/lost, next call, demo, closed amount, `assignedTo`/`marketerId` → `platformSalesTeam`, optional `companyId` once they sign up) with an append-only call/note/status/demo log in `platformLeadActivities` (`leadId`, `at` in ms). `platformSalesTeam` is a roster of outside marketers/agents/callers for assignment and commission — **not logins** (superadmin stays email-allowlisted). `platformFeatureRequests` tracks features/bugs raised on calls (Requested → In progress → Testing → Closed). Pages: `/platform/leads` (board with drag-and-drop / list with bulk assign / insights, day report, CSV-Excel import, CSV export), `/platform/calls`, `/platform/feature-requests` (the Sales team page was replaced by Expenses — `/platform/sales-team` redirects; `platformSalesTeam` data is still used for lead assignment) under `src/pages/platform/leads/`; pure logic in `src/lib/platform/leads.ts` (tested), Firestore access in `src/services/platformLeadsService.ts`. Superadmins read/write these collections directly (no callables). `platformTodos` (reminders/tasks linked to a lead/company). Feature requests move only by step buttons — Start (Requested → In progress), then "Close — move to testing" (required testing instructions; creates a "testing" to-do) — and are closed only by ticking that to-do on To-Do (its bug button sends the request back to In progress — `src/services/platformTodosService.ts`, `/platform/todos`) works the same way.
- **Closing a company permanently** (`Close permanently…` on `/platform/companies/:id`, `platformDeleteCompany` in `functions/src/platform/deleteCompany.js`): superadmin only, typed-name confirmation, irreversible. Erases only that company — tenant documents (matched on `companyId`/`siteId`/`tenantId`, so **a new tenant collection must be added to `TENANT_COLLECTIONS` there**), its users/invites/invoices, role-mapping docs, logins (only those mapped to the same company), `companies/{id}/…` and other company/plant-keyed Storage folders — and cancels its Stripe subscription first. Keeps the audit log, Lumora sales/expense records and Stripe customer/invoices.
- **Expenses** (`/platform/expenses`, `platformExpenses`, superadmin only): Lumora's FirmiCore running costs (hosting, domains, SMS, ads, commissions…) in LKR or USD, monthly/category totals, Stripe income for the same month, and recurring bills that are due but not entered yet (pure logic in `src/lib/platform/expenses.ts`, tested).
- **Billing emails / cancellations**: there are no manual payment reminders — the Stripe webhook emails every active company admin a receipt (plan, amount, next automatic renewal) after each charge. Company admins cancel or ask to leave from the Billing page through `requestCancellation` (`functions/src/billing/cancellations.js`), which always requires a reason (`CancellationReasonDialog`, not dismissable); cancellations made in the Stripe portal without a reason set `companies.cancellationReasonPendingId` and the admin is shown the same window app-wide until they answer. Everything lands in `platformCancellations` (console tab `/platform/cancellations`).
- **There is no centralized RBAC config.** Access is enforced inline, per-route, via a `requiredRoles` array passed to `ProtectedRoute` (`src/components/auth/ProtectedRoute.tsx`) in `src/router/AppRouter.tsx`. `PublicRoute` is the inverse guard for auth pages.
- The sidebar nav (`NAV_ITEMS` in `src/components/layout/AppLayout.tsx`) is a separately-maintained, role-filtered list that *mostly* mirrors route restrictions but can drift (a page reachable by direct URL isn't always in the nav for that role, and vice versa) — when changing access for a role, update both.
- Finer-grained in-page permissions (view vs. edit vs. delete a specific record) are generally ad hoc per component, not centralized. The Machines module is the one exception with an explicit typed permission model: `MachinePermission` / `MachineRolePermissions` in `src/types/machine.ts`.
- Full role × feature access matrix is documented in `FEATURES.md` — check it before changing which roles can reach a module.

### Frontend structure
- `src/pages/` — route-level page components, one subfolder per module (machines, workorders, breakdowns, pm, inventory, contractors, shift, training, triage, triage-builder, analytics, reports, billing, settings, auth).
- `src/modules/` — self-contained feature modules with their own pages/services/hooks (audit, evaluation, kaizen, oee, tpm, fives). **`tpm` and `fives` are built but not wired into the router/nav** — likely superseded by the unified `audit` module; don't assume they're reachable in the live app.
- `src/features/triage/` — newer triage ("knowledge") implementation, distinct from the legacy flow-runner still routed under `src/pages/triage/`.
- **Training has two fully separate module libraries**, told apart by the required `libraryScope` field on `trainingModules` (`'training'` | `'trainee_management'`). Each owns its own hook (`useTrainingLibraryModules` / `useTraineeLibraryModules`, both filtering server-side), component (`components/training/manager/library/TrainingModuleLibrary` / `TraineeModuleLibrary`), settings form, editor routes (`training/manage/modules*` / `training/manage/trainee-modules*`), sample seeder, and validator. They must not import each other or share a query — if something needs an `if` on which library it is, duplicate it instead. Modules predating `libraryScope` are invisible to both until `seed/backfillLibraryScope.mjs` runs.
- **Trainees never write their own result**: quizzes are graded server-side by the `submitTrainingQuiz` callable and no-quiz modules completed by `completeTrainingAssignment` (`functions/src/training/trainingProgress.js`); rules let a trainee write only lesson progress (and the offboard report). `generateTrainingCertificate` issues a certificate (fixed id `cert_<assignmentId>`, shared with the sign-off screen) only for a manager's passed `practicalSignOff` or a server-set `completedVia`, otherwise it reverts the status.
- `src/store/` — Zustand stores (auth, dashboard, handover, pm, reports).
- `src/services/` — cross-cutting business logic / Firestore access (analytics, handover, reports, team performance, trainee program).
- `src/lib/` — utilities: machine health scoring, QR generation, date formatting, RCA, reliability calcs, i18n setup, LOTO gating, etc. Domain-heavy pure functions here are the ones under test in `src/lib/__tests__/`.
- `src/types/` — domain types per feature area; `src/schemas/` — matching Zod validation schemas.
- Path alias `@/*` → `src/*` (configured in both `tsconfig.json` and `vite.config.ts`).

### Plan limits and feature gating
`src/lib/planLimits.ts` is the single source of truth (mirrored for Cloud Functions in `functions/src/lib/planFeatures.js` — keep both in sync). Plans are Starter / Growth (internal id `workshop`) / Factory / Enterprise, matching the pricing page on firmicore.com. Count limits are company-wide: full users and light users (`seatTypeForRole`: floor operators and trainees are light, every other role is full; pending invitations count — `useSeatUsage` in `usePlanLimitCheck.ts`), plants (Starter 1, Growth 3, Factory 5 — multi-plant starts at Growth), machines, inventory parts, PM schedules, work orders per month (60 / 400 / 2,500), breakdown reports per month (40 / 300 / 2,000; the public anonymous QR page can't count, so that cap applies to signed-in reports only), contractors and training modules (0 / 25 / 250 each; checked with `assertWithinPlanLimit` / `checkPlanLimit` at create), AI credits per month (a normal `claudeJson` request = 1 credit, one with web research = 6; counted in `aiUsage/company_<id>_m_<YYYY-MM>` by `consumeAiQuota(…, cost)` and refunded with `refundAiCredits` if the provider fails; mirrored in `functions/src/lib/planFeatures.js`) and analytics history months (informational — the Analytics UI offers at most 12 months, which every plan covers); storage is not limited. Prices, labels and the Enterprise price list live in `src/lib/planCatalog.ts`, which feeds the Billing page tables and the platform console's `/platform/plans` page. Enterprise has no fixed numbers: a company's `enterpriseTier` (Enterprise 1/2/3/Unlimited) and Lumora-set `limitOverrides` (add-ons, grandfathered limits) are merged by `limitsForCompany()` — always read limits through it (via `usePlanLimitCheck` or directly), not `PLAN_LIMITS`. Both fields are in the `companies` rules' protected billing fields and are written only by `platformUpdateCompany` (`setPlan` / `setLimits`). Count limits are checked in the app (create forms and bulk imports) and again on the server: `functions/src/billing/planLimitEnforcement.js` triggers on every new machine, inventory part, PM schedule, plant and user invitation, and removes a record that ranks beyond the plan's limit (oldest are kept; a full copy goes to `planLimitViolations`; `PLAN_LIMIT_ENFORCEMENT=log|off` in `functions/.env` softens it; its counting queries need the composite indexes in `firestore.indexes.json`, and its tests are `rules-tests/planLimitEnforcement.test.mjs` + `src/lib/__tests__/serverPlanParity.test.ts`). Scrapped machines, inactive plants, deactivated users, expired invitations and archived PM schedules take no slot. Seat changes of existing users (role switch, reactivation) and plan-gated modules are still checked in the app only. Work orders created as follow-ups (RCA corrective actions) and by the PM schedulers are not blocked. Plan-gated modules are enforced centrally in `ProtectedRoute` via `featureForPath` (contractors, shift handover, training, safety, MOE, purchase orders, analytics + reports, audits), not per route; the Analytics plants/team tabs use `PlanFeatureGate` (advanced analytics). Server-side checks: `autoPOEmail`/`qrLowStockAlerts` in `sendPoEmails`/`notifyLowStock`, `aiAssist` in `claudeJson`, `analyticsReports` in `generateReport`, `advancedAnalytics` in `generateScheduledReport`. A running free trial unlocks every feature while numeric limits stay Starter's. The Stripe price IDs (`STRIPE_PRICE_*`) must match the prices in `planCatalog.ts`.

### Client-side analytics computation
Dashboards and reports always compute their metrics client-side from operational collections (breakdowns, work orders, contractor jobs, PM history, machines) — they never read `analytics_daily` / `analytics_monthly` / `machine_health`. Every KPI uses the shared definitions in `src/lib/analytics/maintenanceMetrics.ts` (cost = WO parts + labour + the contractor's own charge, dated when the work was done; SLA from work-order deadlines; MTBF/MTTR; cancelled records excluded) and downtime from `src/lib/machineDowntime.ts` (a failed / not-complete sign-off doesn't end a breakdown's downtime). Server copies (`functions/src/lib/maintenanceMetrics.js`, `machineDowntime.js`, `analytics/monthlyAnalytics.js`) feed `analytics_monthly` and `machine_health` for scheduled reports — **change a definition on both sides**; the `*Parity.test.ts` tests fail when they drift. Labour cost comes from `companies/{id}/labourRates/{uid}` (admin/HR set it on the Users page; the `costWorkOrder` function prices logged hours and parts).

### Machine health scoring
The 0–100 health score (`src/lib/machineHealth.ts`: starts at 100, deducted for breakdowns by severity and overdue/missed PM within a trailing 90-day window, −5 under maintenance, credited for on-time PM) is computed **server-side** by `functions/src/machines/machineHealth.js` on breakdown / PM / work-order / machine-status changes and daily, and stored on `machines/{id}.healthScore` (+ `healthScoreUpdatedAt`) and `machine_health`. Nobody sets it by hand — the machine form shows it read-only and `firestore.rules` reject client edits. See `MODULE_3_MACHINES_README.md` for the algorithm — but note its permissions table is stale (says `trainee` has no machine access; the live router grants view access).

### Cloud Functions (`functions/`)
Organized by feature area under `functions/src/` (analytics, contractors, handover, inventory, invitations, lib, pm, reports, training, triage), entry point `functions/index.js`. Uses `firebase-admin` / `firebase-functions` v7, plus `puppeteer-core` + `@sparticuz/chromium` for server-side PDF/rendering work and `googleapis`/`nodemailer` for Sheets/email integrations. Node 22 runtime. Lint runs automatically as a `predeploy` hook (`firebase.json`).

### Notifications
The bell reads only the `notifications` collection. A notification reaches **only the roles and people it names** — admin and plant_manager are not copied on everything (they see only what names their role or them, a plant manager only from their own plant), and every entry shows its plant and, when known, its department (`notificationLocationLabel`; `actorDepartment` is display-only, `department` also narrows department-scoped readers). Client code writes through `createNotification()` (`src/services/notifications.service.ts`); Cloud Functions must write through `sendNotification()` (`functions/src/lib/notify.js`), which builds the same shape (oversight copy, targeting) and takes an optional `dedupeKey` so retried triggers/schedules never post twice. Never write to `companies/{id}/notificationLogs` — nothing reads it. Automation in `functions/src/notifications/`: `escalateUnackedBreakdowns` (re-alerts at 30/60 min if a breakdown is still `reported`) and `cleanupOldNotifications` (daily, deletes after 45 days). Rules let readers change only `readBy`/`read` on a notification.

### Firestore/Storage
- `firestore.rules` and `storage.rules` are the source of truth for server-side access control — always check these when changing what a role/query can read or write, since client-side route guards are not a security boundary on their own.
- `storage.rules` treats only **non-anonymous** accounts as signed in (the public QR breakdown page no longer signs visitors in at all: it calls the rate-limited `getPublicMachine` / `submitPublicBreakdown` callables, which write the ticket with admin rights, and uploads nothing; `publicRateLimits` holds its counters, server-only — add a Firestore TTL policy on `expireAt` to sweep them), and limits every company-keyed path (`companies/`, `workorders/`, `breakdowns/`, `kaizen/`, `audit*/`, `evaluation_attachments/`, `safetyTrainingSubmissions/`, `triage/{companyId}/`) to the `companyId` **custom claim** on the login token — storage rules can't read the named Firestore database. The claim is kept equal to `users/{uid}.companyId` by `onUserMappingWritten` and, for older tokens, by `syncCompanyClaim` (called from `useAuthInit` via `ensureCompanyClaim`). Anything else calling `setCustomUserClaims` must merge, not replace, existing claims. Contractor documents/technician files and inventory part warranty files are uploaded under `companies/{companyId}/contractors/…` and `companies/{companyId}/inventoryParts/…`; the legacy top-level `contractors/` and `inventoryParts/` folders are closed to all client access (older files still open through their saved token download URLs, which bypass rules). New file uploads must always start with `companies/{companyId}/` (or another company-keyed root).
- Callables that take a `companyId` from the client must verify membership server-side (e.g. `requireCompanyMember` in `functions/src/handover/shared.js`) — `request.auth` alone also matches anonymous and other companies' users.
- Deploys run from GitHub Actions on merge to `main`: hosting and functions in parallel; Firestore/Storage rules + indexes only **after** the functions deploy succeeds (`firestore-rules-deploy.yml`, `workflow_run`), since rules can depend on functions (e.g. the `companyId` claim). Each workflow also has a manual "Run workflow" button (`workflow_dispatch`).
- `firestore.indexes.json` holds required composite indexes; new queries that filter/sort on multiple fields (almost always including `siteId`) typically need a matching entry here.

## Known gaps (don't silently "fix" without asking — may be intentional or a larger cleanup)
1. Role naming drift: `AUTHENTICATION_README.md` calls one role `maintenance_supervisor`; the actual code uses `supervisor`.
2. `src/modules/tpm` and `src/modules/fives` are fully built but orphaned (not routed/navigable).
3. Nav vs. route access can drift for a given role/page (e.g. Evaluations is reachable by supervisors via URL but not shown in their nav).
4. `UserRole` type is declared independently in both `src/types/auth.ts` and `src/types/breakdown.ts`.
5. **Department isolation is client-side only**: `firestore.rules` defines `isSameDepartment()` / `isDepartmentScopedRole()` but no rule uses them, so technician / trainee / supervisor / floor_operator are confined to their department by the app's queries, not by the rules (company and plant isolation *are* rule-enforced). Server code that reads tenant data with admin rights on a user's behalf (e.g. the AI history in `claudeJson`) must apply plant **and** department scope itself. Storage files are company-scoped only.
